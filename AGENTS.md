# ATHAR Frontend — API notes

## Goal
Consumer for the ATHAR backend API (`/Users/faycalamrouche/Desktop/ATHAR/Athar`,
FastAPI, OpenAPI contract). Two clients, both generated from the same spec:
a Next.js dashboard and a Flutter mobile app.

## Clients
- **Dashboard (Next.js)** — `dashboard/src/lib/api-types.ts` generated by
  `openapi-typescript` from `openapi.json` (synced from the backend via
  `scripts/sync-spec.mjs` — copies `../Athar/docs/specs/openapi.json`).
  `dashboard/src/lib/client.ts` is a hand-written fetch layer keyed by path,
  typed with the generated types. Generate: `cd dashboard && npm run generate:api`.
- **Mobile (Flutter)** — `mobile/lib/core/api/generated/athar_api` generated by
  `openapi_flutter_gen`. `mobile/lib/core/api/api_client.dart` is a facade that
  keeps presentation-model signatures stable (getwilayas, getPoiDetail, chat,
  ...) while delegating transport + serialization to the generated `ApiClient`.
  Regenerate with `scripts/generate-mobile-api.sh` (post-processes two
  generator bugs: `?.toJson()` on nullable sealed wrappers + missing `toFormData`
  on multipart upload bodies). Both clients are wired to a spec-driven build, so
  `/docs`, `/redoc` are gated behind debug in the backend, and the API is
  hardened (allowed_hosts loopback, rate limits, OTP lockout).

## Operation ids
- Backend S5 set a deterministic, path-based operationId scheme
  (`app/api/v1/operation_ids.py`): `GET /api/v1/discover/wilayas` →
  `get_discover_wilayas`. This makes the generated client method/type names
  stable and clean across regenerations.
- The names flow into `api-types.ts` (dashboard) and the Dart API classes
  (mobile). Client regeneration is mechanical:
  1. Regenerate the backend spec (`cd Athar && python scripts/generate_openapi.py`),
     run `scripts/check_spec.sh --refresh-base` if breaking-change gate trips.
  2. Dashboard: `cd dashboard && npm run generate:api`, verify `tsc --noEmit`.
  3. Mobile: `./scripts/generate-mobile-api.sh`, then `flutter analyze` (generated
     dir is excluded), `flutter test`, `flutter build web --release`.
  4. Commit both repos separately (backend first, then frontend).

## S6 — BFF assessment (recommend-only, no code)
- **Current**: 87 paths / 112 operations; two generated clients consume the API
  directly over HTTP. Auth is short-lived bearer tokens (access + rotating
  refresh); no server-side long-lived secrets needed on the client. Clients
  derive types + errors for free from the shared OpenAPI spec.
- **Recommendation: no BFF.** A backend-for-frontend would add an extra hop and a
  second waypoint to desync, without removing real pain today.
- **Re-evaluate a BFF only when one of these is true:**
  1. A third client appears that needs a meaningfully different contract.
  2. Clients start aggregating many endpoints per screen (today each detail view
     maps ~1 endpoint).
  3. Cross-cutting per-client concerns (rate limiting, feature flags, auth shape)
     growing beyond what CDN/middleware can express.
  4. The public spec must trim sensitive fields/routes that all clients shouldn't
     see (a BFF can act as a filter).
- If one is adopted, build it as a thin proxy regenerated from the same spec
  (keep generated types both sides), never a hand-maintained overlay.
